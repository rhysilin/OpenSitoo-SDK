# 受邀测试完整流程

[文档首页](/) · [下载工具](/downloads) · [身份与组织](/center/identity) · [测试发布](/center/publishing) · [目录安装](/center/catalog) · [CI与反馈](/center/ci-support)

适用版本：开发者中心0.4.0、Desktop0.0.33、SDK0.0.11、共享工具包0.36.0、发布工具0.2.0，Windows和Node24的受邀本机测试。本文帮助两位开发者分别开发一个应用、复用同一能力，并完成发布、使用和兼容更新。示例业务为纯文本规范化，不调用收费模型；对话使用手动提案。

## 1. 取得环境和记录单

向环境操作者取得中心地址、自己的统一身份账号、组织邀请、组织命名空间、专用Desktop启动入口及原始记录单。中心和Desktop都需要登录，但目录读取凭据、项目发布凭据与模型令牌各有用途，不能互换。仅本机运行的127.0.0.1地址只能在同一台电脑使用。

同机分别试用时，每人使用各自的浏览器资料目录、Desktop数据目录和仓库外工程目录。先正常退出上一位Desktop及登录窗口，再启动自己的入口，不复用对方登录状态或秘密。记录开始时间；首次在已安装页面取得共享能力结果作为首次成功时间，单独记下等待审核耗时。求助一次记录一次，失败保留阶段、错误码和requestId，不填写密码或业务正文。

## 2. 接受邀请和下载公开工具

在中心点击统一身份登录，核对姓名及身份标识，接受组织邀请，再切到共同组织。组织owner/admin预先申请组织命名空间；developer只能使用已有的组织命名空间，个人范围新建命名空间不能用于共同组织项目。检查双方均为developer，不拥有平台reviewer/publisher。

从[下载页](/downloads)取得共享能力工具包0.36.0和测试发布工具0.2.0，核对显示的SHA256后解压。另需本地签名浏览器宿主时下载包管理工具。公开工具不需要平台源码，禁止导入平台私有目录。受邀Desktop开发版由环境操作者提供专用入口，当前下载页不提供正式Desktop生产安装包。

## 3. 创建两个应用和一个共同能力

共享工具模板包含core、app-a、app-b，创建命令如下。替换为自己的工具位置和一个尚不存在的工程路径，Windows目录可使用正斜杠。

```powershell
node C:/Sitoo/capability-kit/sitoo-project.mjs create C:/dev/my-invited-project
```

第一位开发者负责共同core及自己的app-a；第二位开发者在另一个工程负责自己的app-b，依赖第一位已经发布的core。各自修改manifest中的包/能力标识和调用绑定，使用操作者分配的组织命名空间，例如your-team/core、your-team/app-a、your-team/app-b与your-team/normalize；保持精确依赖版本一致。不要只改包名而遗漏能力id、调用文件或绑定。详见[包与依赖](/capabilities/packages)、[独立页面](/capabilities/pages)、[共享对话](/capabilities/conversation)。

第一位先在中心创建类型为capability的core项目，选择正确组织范围，填写署名、许可、SDK版本。第二位读取已发布core的精确版本/摘要和能力声明，再创建自己的application项目。core项目必须明确设置organization可见性；默认private时其他普通开发者不能读取。第二位无须复制或修改共同能力的实现，也不能用本地相似函数替代复用。

## 4. 测试、提交与正常审核

使用模板build.mjs构建公共发布物，具体命令和凭据配置见[完整测试发布教程](/center/publishing)。项目发布凭据只允许自己的项目test提交/查询。首次可按教程直接submit；随后按[本地CI教程](/center/ci-support)准备package.json、固定package-lock.json、test.mjs并完成ci命令。CI通过仅表示提交已受理。

共同core先完成审核、签名并推广test渠道，应用再提交与推广。平台由独立reviewer审核、publisher签名；开发者等待正常审核，不能自行签发平台密钥或让操作者代改工程。失败时保留requestId与发布号，查询原记录再修复；已保存的原提交使用同字节/版本重试，不制造重复发布。被拒版本遵循发布教程修订后重新提交，不覆盖原记录。

## 5. 安装并验证两个入口

分别登录自己的Desktop。中心创建本范围只读目录凭据，从可信操作者确认目录地址、公钥与命名空间，按[目录接入](/center/catalog)连接。不要从未核对的包自动信任公钥。

刷新目录，预览精确应用及完整依赖闭包，明确确认安装，再分别授予application和conversation。页面输入带两端空格的文字，预期得到去两端空格并转大写的结果；内部空格保持。手动对话调用同一normalize能力，记录taskId/requestId和结果。两个应用应复用同一个core版本，任务与授权仍相互隔离。页面成功不代表对话已经通过，两项分别记录。

## 6. 兼容更新、撤回与支持

按[兼容示例](/support/examples)提交兼容新版本并经过正常审核，客户端刷新后明确确认更新。旧数据、原taskId及结果必须保留，查询原任务不再次执行。活动或unknown任务锁定原版本时不应强制更新；记录拒绝和原任务可查的结果，由操作者提供适合的对照场景，不能为了演示清掉任务。

撤回测试版本后，刷新目录和确认新安装都应拒绝该候选；已有安装、数据和历史任务保留。撤回不等于卸载或远程删数据。跨组织访问与权限升级应拒绝，正常403/404记录为权限验证结果。

遇到阻塞在中心项目支持里提交最小复现，附requestId/发布号；不要粘贴令牌、密码或完整业务正文。负责人处理并答复后由提出问题的开发者本人复测，确认修复再关闭。完成原始记录单，保留失败、求助和文档缺口；操作者不能代填成功。

## 完成判断

两位分别完成独立应用、真实共享能力复用、提交/审核/安装、页面与对话、更新/撤回和反馈闭环，才算本次受邀流程完成。纯本地预检、自动化报告、下载成功或空白记录不能代替本人操作。生产部署、正式费用、真实Safari和完整人工无障碍验证不由本流程推定通过。
